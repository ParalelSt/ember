# Custom Themes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Plan only: no product code was written while drafting this.

**Goal:** A person picks how their Ember looks. Five ready-made themes (Ember, today's red on black, stays the default and stays byte-identical), a small editor where they change a handful of colours with a picker and see real app pieces update live, a readability guard so nothing becomes unreadable, and the choice follows the account to phone, desktop and web with no flash of the wrong theme on load. Themes can be shared with friends as a code.

**Architecture:** Every colour in the app already flows through about 30 CSS custom properties on `:root` in `apps/web/app/globals.css`, mapped into Tailwind 4 by `@theme inline` as `--color-*`. A theme is eight colours (the *inputs*); a pure function in `lib/theme/derive.ts` turns them into the full set of 30 (plus two new ones, `--ember-foreground` and `--art`), so any custom theme stays coherent. The Ember preset applies **no overrides at all**: the CSS defaults are the theme, which is what makes it byte-identical to today. Any other theme is applied as inline custom properties on `<html>`. The server already reads the `pb_auth` cookie in the root layout, and that cookie carries the whole users record, so the root layout renders the person's theme into the first HTML byte (no flash, no extra request, no rebuild). The account holds the theme in a `users.theme` JSON field (`pb_hooks/ensure_theme_field.pb.js`) behind `GET/PATCH /api/theme`, mirrored in a persisted zustand store (`ember.theme.v1`) the same way the plugin switches already are. Native shells get one small call each (`EmberTheme.apply` on Android, `theme_apply` on desktop) so the bars, the pre-load background and the title bar follow.

**Tech stack:** Next.js 16.2.6 (`apps/web`; read `node_modules/next/dist/docs/01-app/**` at the repo root before any Next-specific code: `apps/web/node_modules` is a symlink into the main checkout), Tailwind 4 CSS-first tokens, PocketBase 0.22 (JS SDK 0.27), zustand 5 with `persist`, vitest + happy-dom + Testing Library, playwright-core browser tests under `tests/`, Capacitor 7 Android (Kotlin, Robolectric JVM tests), Tauri 2.11 (Rust). No new JS dependencies: the colour picker is the native `<input type="color">`, the OKLCH maths is about 80 lines of plain TS.

## 1. Theme model

### 1a. What a person edits (the eight inputs)

| Input | Today (Ember) | Drives |
| --- | --- | --- |
| `background` | `oklch(0.16 0.005 260)` | `--background`, and the base for every derived surface |
| `surface` | `oklch(0.20 0.005 260)` | `--surface`, `--card`, and the steps above it |
| `text` | `oklch(0.98 0 0)` | `--foreground` and every `*-foreground` |
| `mutedText` | `oklch(0.70 0.005 260)` | `--muted-foreground` |
| `accent` | `oklch(0.68 0.20 25)` | `--ember`, `--ring`, `--sidebar-primary`, `--sidebar-ring`, `--cover-from` |
| `accentHover` | `oklch(0.78 0.13 25)` | `--ember-soft` |
| `border` | `oklch(1 0 0)` at 8% | `--border` (8%), `--input` (12%), `--sidebar-border` (6%) |
| `sidebar` | `oklch(0.13 0.005 260)` | `--sidebar` and the sidebar hover step |

The editor shows three of them as **Basics** (background, accent, text) and five under **More** (surface, muted text, accent hover, border, sidebar). Changing a Basic re-fills every More value the person has not touched, using the auto rules in 1c, so "pick a background and an accent" already gives a whole theme. A touched More row is pinned until Reset.

Naming trap to document in code: shadcn's `--accent` / `--accent-foreground` is a *hover surface*, not the brand colour. The brand colour is `--ember`. In the editor the word "Accent" means `--ember`.

### 1b. Derivation (`lib/theme/derive.ts`, pure)

`derive(inputs: ThemeInputs): ThemeVars` returns every variable below. All maths in OKLCH; `L`, `C`, `H` are the input's own components unless a rule says otherwise. `+0.04` means "add to L, clamp 0..1".

| Variable | Rule | Ember result |
| --- | --- | --- |
| `--background` | background | `0.16 0.005 260` |
| `--foreground`, `--card-foreground`, `--popover-foreground`, `--primary`, `--secondary-foreground`, `--accent-foreground`, `--sidebar-primary-foreground`, `--sidebar-accent-foreground` | text | `0.98 0 0` |
| `--surface`, `--card` | surface | `0.20 0.005 260` |
| `--surface-2`, `--muted` | surface L+0.04 | `0.24 0.005 260` |
| `--popover` | surface L+0.02, C x 1.2 | `0.22 0.006 260` |
| `--secondary` | surface L+0.06 | `0.26 0.005 260` |
| `--accent` (shadcn hover surface) | surface L+0.10 | `0.30 0.005 260` |
| `--primary-foreground` | background L+0.02 | `0.18 0.005 260` |
| `--muted-foreground` | mutedText | `0.70 0.005 260` |
| `--border` | border at alpha 8% | `1 0 0 / 8%` |
| `--input` | border at alpha 12% | `1 0 0 / 12%` |
| `--sidebar-border` | border at alpha 6% | `1 0 0 / 6%` |
| `--ember`, `--ring`, `--sidebar-primary`, `--sidebar-ring`, `--cover-from` | accent | `0.68 0.20 25` |
| `--ember-soft` | accentHover | `0.78 0.13 25` |

| `--sidebar` | sidebar | `0.13 0.005 260` |
| `--sidebar-foreground` | text L-0.03 | `0.95 0 0` |
| `--sidebar-accent` | sidebar L+0.09 | `0.22 0.005 260` |
| `--destructive` | fixed, not themed | `0.65 0.22 25` |
| `--ember-foreground` (new) | text if WCAG contrast(text, accent) >= 3.0, else background | text (white on ember red rates about 3.2:1) |
| `--art` (new) | `oklch(0 0 0)` when scheme is dark, else background L-0.08 | `0 0 0` |
| `scheme` (not a var) | `'dark'` when background L < 0.5 else `'light'` | dark |

Every rule above reproduces today's `:root` value for Ember numerically (the test in Task 1 parses `globals.css` and checks each). Light-scheme rules (`--art`, border) exist so a light preset later is values only; no light preset ships in v1 (owner question 2).

The **auto rules** the editor uses to fill More from Basics (also in `derive.ts`, as `autoFill(basics, pinned)`):

- surface = background L+0.04
- sidebar = background L-0.03
- mutedText = L: background L + (text L - background L) x 0.66; C and H from background
- accentHover = accent L+0.10, C x 0.65
- border = `oklch(1 0 0)` for dark schemes, `oklch(0 0 0)` for light

Auto-filling from Ember's three Basics gives Ember's five More values to within 0.005 in L (tested).

### 1c. The stored shape (`lib/theme/model.ts`)

```ts
export type Oklch = [l: number, c: number, h: number]; // 3, 3 and 0 decimals when serialised
export interface ThemeInputs {
  background: Oklch; surface: Oklch; text: Oklch; mutedText: Oklch;
  accent: Oklch; accentHover: Oklch; border: Oklch; sidebar: Oklch;
}
export type PresetId = 'ember' | 'midnight' | 'forest' | 'nebula' | 'mono';
/** What the account stores in users.theme and the store caches. */
export interface ThemeDoc {
  v: 1;
  preset: PresetId;        // the base the person started from
  custom?: ThemeInputs;    // present once edited; wins over preset
  name?: string;           // max 40 chars, shown for a custom theme
}
export const DEFAULT_THEME: ThemeDoc = { v: 1, preset: 'ember' };
```

`parseThemeDoc(raw: unknown): ThemeDoc` never throws: unknown version, unknown preset or an out-of-range input (L outside 0..1, C outside 0..0.4, H outside 0..360, wrong tuple length) falls back to `DEFAULT_THEME`, one bad field falls back for that field only. `resolveInputs(doc)` gives the effective inputs (custom, else the preset's). `isDefault(doc)` is true when the resolved inputs equal Ember's, which is the "apply no overrides" case. A serialised doc is about 220 bytes; a test asserts a maximal doc (longest name, all numbers at full width) stays under 400 bytes, because it travels inside the `pb_auth` cookie (section 3).

Share code (`lib/theme/share.ts`): `encodeShareCode(doc)` gives `ember-theme:1:<base64url of JSON {name, inputs}>` (about 300 characters); `decodeShareCode(text)` accepts that, or a pasted JSON object, trims whitespace, and returns `ThemeDoc | null` through `parseThemeDoc`. A code carries no account data, only colours and a name.

### 1d. Colour maths (`lib/theme/oklch.ts`, pure, no deps)

- `hexToOklch(hex)`, `oklchToHex(oklch)` via linear sRGB and OKLab using Ottosson's matrices. sRGB linear to LMS: `l = 0.4122214708 r + 0.5363325363 g + 0.0514459929 b`, `m = 0.2119034982 r + 0.6806995451 g + 0.1073969566 b`, `s = 0.0883024619 r + 0.2817188376 g + 0.6299787005 b`; cube roots; `L = 0.2104542553 l' + 0.7936177850 m' - 0.0040720468 s'`, `a = 1.9779984951 l' - 2.4285922050 m' + 0.4505937099 s'`, `b = 0.0259040371 l' + 0.7827717662 m' - 0.8086757660 s'`. Inverse: `l' = L + 0.3963377774 a + 0.2158037573 b`, `m' = L - 0.1055613458 a - 0.0638541728 b`, `s' = L - 0.0894841775 a - 1.2914855480 b`; cube; `r = 4.0767416621 l - 3.3077115913 m + 0.2309699292 s`, `g = -1.2684380046 l + 2.6097574011 m - 0.3413193965 s`, `b = -0.0041960863 l - 0.7034186147 m + 1.7076147010 s`; then the sRGB transfer curve. `C = sqrt(a^2 + b^2)`, `H = atan2(b, a)` in degrees, 0..360; C below 0.001 serialises as 0 with H 0.
- `oklchToHex` gamut-maps by reducing C (binary search, 16 steps) until every channel is inside 0..1, which is what a browser does for an out-of-gamut `oklch()` near enough for a picker round trip.
- `contrast(a: Oklch, b: Oklch, alphaOverB?)`: WCAG 2.x contrast ratio from linear-sRGB relative luminance (`0.2126 r + 0.7152 g + 0.0722 b`), ratio `(lighter + 0.05) / (darker + 0.05)`; a translucent colour is composited over the other first.
- `formatOklch(oklch, alphaPct?)` gives the CSS string `oklch(0.16 0.005 260)` or `oklch(1 0 0 / 8%)`; `parseOklch(css)` reads the same (used by the globals.css test and by `tabScore.ts`, which today paints on a canvas to read a token).

Reference values for the tests: `#ffffff` is L 1, C 0; `#000000` is L 0; `oklch(0.68 0.20 25)` is about `#fb5855` (channels within 2); white on it rates about 3.2:1; text on Ember's background about 18:1; muted text on it about 7:1. Round trip hex to oklch to hex is exact for every 8-bit grey and within 1 per channel for 200 random colours.

## 3. Applying a theme

### 3a. On the page

`lib/theme/css.ts`: `varsToStyle(vars): Record<string, string>` gives the inline style map (`{'--background': 'oklch(...)', ...}`) for a non-default theme and `{}` for Ember. `applyToDocument(doc, root = document.documentElement)`:

1. For every variable in section 1b, `root.style.setProperty(name, value)`; for the default, `root.style.removeProperty(name)` for each so the CSS wins again.
2. `root.classList.toggle('dark', scheme === 'dark')` and `root.style.colorScheme = scheme`. All v1 presets are dark, so the class stays; the toggle exists for a light theme later and for imported codes.
3. `meta[name="theme-color"]` content = background as hex (create the meta if the server did not render it).
4. `window.dispatchEvent(new CustomEvent('ember:theme', { detail: { scheme, background } }))` so the tab score (`lib/tabScore.ts` reads tokens once at init) and the native bridge can react.

### 3b. No flash, server side

The root layout (`apps/web/app/layout.tsx`) already calls `createClient()` and reads `pb.authStore.record` from the `pb_auth` cookie on every request. The PocketBase SDK's `exportToCookie` puts the **whole record** in that cookie (confirmed in `node_modules/pocketbase/dist/pocketbase.es.js`: it only collapses the record to `id`/`email` when the cookie would exceed 4096 bytes). So:

- `lib/theme/fromRecord.ts`: `themeFromRecord(record: unknown): ThemeDoc` = `parseThemeDoc(record?.theme)`.
- Root layout: `const theme = themeFromRecord(pb.authStore.record)`; render `<html lang="en" className={cn(inter.variable, scheme === 'dark' && 'dark')} style={varsToStyle(derive(resolveInputs(theme)))}>` (an empty object for Ember, so today's markup is unchanged). `suppressHydrationWarning` is already on `<html>`.
- `export async function generateViewport(): Promise<Viewport>` replaces the static `viewport`: `themeColor` = the theme's background as hex (one value, no media query; the second entry today, `#ff5a3a` for light-scheme browsers, goes: see owner question 10). The rest of the viewport object is unchanged. Reading cookies makes the layout dynamic, which it already is.
- The first byte of HTML carries the theme; CSS variables on `<html>` apply before any script runs. There is no client-side theme script and nothing to race.

Keeping the cookie fresh: `PATCH /api/theme` returns the saved doc; the client then calls `pb.authStore.save(pb.authStore.token, { ...pb.authStore.record, theme })` so `lib/pocketbase/client.ts`'s `onChange` rewrites `document.cookie` at once. A hard reload right after saving therefore renders the new theme server-side. `proxy.ts` also rewrites the cookie from a fresh `authRefresh` on every request, so another device's change reaches this device's cookie on its next navigation.

Cookie budget: the record already holds email, name, avatar filename, the `plugins` JSON and the privacy bools; adding about 220 bytes of theme keeps a typical cookie around 1.5 KB. If a record ever crosses 4096 bytes the SDK drops it to `id`/`email`, `themeFromRecord` returns the default, and the client store corrects the page after hydration (a one-time flash, logged as a warning through `logger.warn('theme', 'cookie record stripped')` so it is visible in bug reports). The Task 2 unit test pins the 400-byte ceiling on a doc.

### 3c. Client store and provider

`stores/useThemeStore.ts` (zustand, `persist`, name `ember.theme.v1`, partialize to `{ doc }`), modelled on `useSettingsStore`:

- `doc: ThemeDoc`, `setDoc(doc)` (optimistic: apply locally, PATCH, roll back on failure unless something newer replaced it), `reset()` = `setDoc(DEFAULT_THEME)`.
- `userId`, `loaded`, `loadTheme(userId)` (once per user id; GET `/api/theme`; a missing account value migrates this device's doc up, first device wins, exactly like `loadPlugins`), `resetThemeSync()` on sign-out. The `editedDuringLoad` guard is reused so an edit made while the load is in flight is not overwritten.
- `hydrateFromServer(doc | null)`: called once on mount by the provider with the layout's server-known doc; a non-null server doc wins over the localStorage cache (the cookie record is at least as fresh as the account); null leaves the cache.

`components/providers/ThemeApplier.tsx` (client, mounted in the root layout inside `AuthProvider`, next to `LoggerInit`): takes `initial: ThemeDoc | null`; on mount calls `hydrateFromServer(initial)`; subscribes to the store and calls `applyToDocument(doc)` on every change and once on mount; calls `notifyShell(...)` from `lib/theme/native.ts` (Task 5) after each apply. `AuthProvider` gains one effect next to the plugins one: `if (userId) void useThemeStore.getState().loadTheme(userId); else resetThemeSync()`.

`lib/api.ts` gains `getTheme(): Promise<ThemeDoc>` and `updateTheme(doc: ThemeDoc): Promise<ThemeDoc>`.

### 3d. Offline and signed out

- Signed out (`/auth`, `/privacy`, `/terms`): the cookie has no record, so the layout renders the default Ember theme; the persisted store still holds the last signed-in theme on that device, and `hydrateFromServer(null)` keeps it, so `ThemeApplier` applies the cached theme after hydration. Recommendation (owner question 8): signed-out pages stay on Ember, which means `ThemeApplier` does not apply a cached doc when there is no user; `resetThemeSync` keeps the cache so the theme is back the moment the person signs in. One line, and it stops one friend's theme colouring the sign-in page on a shared computer.
- Offline in the browser: Ember has no service worker (`public/sw.js` is a kill switch), so an offline browser cannot load a page at all; nothing to theme.
- Offline on Android: Capacitor shows the bundled `apps/mobile/public/offline.html` from `https://localhost`, a different origin with no cookies. Task 5 publishes the theme variables into that page from the native side, and `offline.html` reads them with `var(--background, #0a0a0a)` fallbacks. Desktop has no offline page.

4. **Readability**: `lib/theme/guard.ts`, `checkTheme(inputs): Finding[]` where a finding is `{ pair, ratio, level: 'ok' | 'warn' | 'fail', fix?: ThemeInputs }`:

   | Pair | ok | warn | fail |
   | --- | --- | --- | --- |
   | text on background | >= 7 | 4.5 to 7 | < 4.5 |
   | text on surface-2 (hover rows) | >= 7 | 4.5 to 7 | < 4.5 |
   | mutedText on surface | >= 4.5 | 3 to 4.5 | < 3 |
   | ember-foreground on accent (buttons) | >= 4.5 | 3 to 4.5 | < 3 |
   | accent on background (links, active nav, `text-ember` has 117 uses) | >= 4.5 | 3 to 4.5 | < 3 |
   | sidebar-foreground on sidebar | >= 7 | 4.5 to 7 | < 4.5 |

   `fix` moves the offending input's L away from its partner in 0.02 steps (up to 20) with C and H kept, until the pair is at least "warn". The UI shows findings under the rows as one line each ("Muted text on cards: 2.4:1, hard to read") with a "Fix it" button that applies `fix`. Nothing is adjusted silently. ## 7. Native shells

Both shells load the host's page, so the page itself is themed by sections 3 and 4 with nothing native. What native must follow is the chrome around the page: Android's system bars and the blank before the first HTML byte, desktop's window background and title bar, and the Android offline page.

`lib/theme/native.ts` (web): `notifyShell(resolved: { background: hex; scheme; vars: Record<string,string> })` uses `detectShell()` from `lib/playback/detectShell.ts`: `'capacitor'` calls `window.Capacitor.Plugins.EmberTheme.apply({ background, scheme, vars: JSON.stringify(vars) })`; `'tauri'` calls `window.__TAURI_INTERNALS__.invoke('theme_apply', { background, scheme })`; `'web'` does nothing. Every call is wrapped so a missing plugin (an old APK) is a no-op, and it runs after `applyToDocument` in `ThemeApplier`.

**Android** (`apps/mobile/android/app/src/main/java/app/ember/music/`):

- `ThemeColors.kt` (pure, JVM-tested): `parseHex("#rrggbb"): Int?`, `isLight(argb): Boolean` (relative luminance above 0.4), `script(varsJson): String` building the same self-contained document-start script `SafeAreaInsets.script` builds, setting each variable on `document.documentElement` with the readystatechange retry.
- `EmberThemePlugin.kt` (`@CapacitorPlugin(name = "EmberTheme")`): `apply(call)` stores `background`, `scheme`, `vars` in `SharedPreferences("ember_theme")`, then on the main thread `ThemeColors.applyToWindow(activity, webView, background, light)`: `webView.setBackgroundColor`, `window.decorView.setBackgroundColor`, `WindowInsetsControllerCompat(window, decorView).isAppearanceLightStatusBars = light` and `isAppearanceLightNavigationBars = light`, and below SDK 35 `window.statusBarColor` / `window.navigationBarColor` = background (on 35 the bars are transparent and drawn over the page, so the page's own background is the bar colour; only the icon lightness matters). `registerPlugin(EmberThemePlugin.class)` in `MainActivity.onCreate` next to the others.
- `MainActivity`: after `publishSafeAreaInsets()`, `applyStoredTheme()` reads the prefs and calls the same `applyToWindow` before the page loads (so the blank between splash and first byte is the theme's background, not white or black), and registers `ThemeColors.script(vars)` as a document-start script scoped to the offline origin (`getBridge().getErrorUrl()`'s origin, the way `injectBridgeIntoErrorPage` derives it) so `offline.html` gets the variables. The splash itself (`res/drawable*/splash.png`, `Theme.SplashScreen`) stays the brand red on black (owner question 9).
- `offline.html`: the `<style>` block uses `var(--background, #0a0a0a)`, `var(--foreground, #ededed)`, `var(--surface, #1f1f1f)`, `var(--ember, #f59e0b)` fallbacks; no other change.

**Desktop** (`apps/desktop/src-tauri/`):

- `src/theme.rs`: `#[tauri::command] theme_apply(app, background: String, scheme: String)`: parse the hex (`parse_hex`, unit tested), `window.set_background_color(Some(Color(r, g, b, 255)))`, `window.set_theme(Some(match scheme { "light" => Theme::Light, _ => Theme::Dark }))` (Windows title bar and the macOS title bar follow the window theme), and write `{ "background": "#..", "scheme": ".." }` to `app.path().app_config_dir()/theme.json` (`store_theme` / `load_theme`, unit tested with a temp dir).
- `lib.rs` `.setup`: `theme::apply_stored(&handle)` right after the media controls, so the window's background is the stored colour before the remote page arrives. `theme_apply` goes in `permissions/app-commands.toml` (a remote origin is denied every command not named there) and in `generate_handler!`.
- `tauri.conf.json`: no change (`backgroundColor` in config would be a static value; the stored one is applied at startup instead). Tauri 2.11 has `set_background_color` and `set_theme` on `WebviewWindow`; `tauri-utils 2.9.3` config confirms the fields exist.

**Web `theme-color` meta**: rendered by `generateViewport` from the cookie (Task 2) and kept current by `applyToDocument`. `public/manifest.webmanifest`'s `theme_color` / `background_color` stay static (PWA install is de-emphasised, the SW is a kill switch).
