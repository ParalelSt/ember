## 1. The stalls (reports 2 and 3)

### What the reports show

- Report 2: `-14.0s ended`, `-14.0s load (x2)`, `-3.2s` stall "on a second
  attempt". 10.8 s from the loads to the final error.
- Report 3: `-68.8s ended`, `load (x2)`, `-58.1s` stall "on a second attempt"
  (10.7 s). Then `-9.4s load (x2)` and `-2.5s` a stall WITHOUT "second
  attempt": that one is the first, superseded load of the pair, which is
  never retried and whose failure main still reports (bughunt P03). The
  current load's own result would have come after the report was sent.
- No stream errors on the host. The host answered every request.

### The songs

Fetched with the main checkout's `player.py` into a scratch MUSIC_DIR (yt-dlp
2026.08.19, with ffmpeg):

| id | length | size | layout |
|---|---|---|---|
| uV18CIbSXZo | 6:22 | 6.2 MB | remuxed: ftyp, moov (67 KB), free, mdat |
| OmeUVcUuV10 | 5:52 | 5.7 MB | remuxed: ftyp, moov (61 KB), free, mdat |

Long, but ordinary, and not fragmented. For a remuxed file the engine keeps
the seekable decoder, and building it reads the file's last 64 KB (symphonia
skips over the mdat and reads its tail). That is one extra Range request per
load: `whole`, then `6112655-6178190`, then the middle once it plays
(`stall_repro::measure` on the real file shows exactly these three).

### The mechanism

`stream-download` answers that tail read with a new request, and stops
reading the first response while it waits. Until the tail answers, nothing
arrives, and after 3 s of nothing the engine gives up ("stopped arriving
while decoding"). How long the tail waits is not the host's doing: its answer
queues behind every byte already on its way to the listener, the first
response's included. On a slow link with deep buffers (the Tailscale Funnel)
that is seconds. With `load (x2)` there are two first responses and two tail
requests on the same link, so the wait roughly doubles. The stall retry does
not help, because the second attempt makes the same requests on the same
link.

### Reproduced

`apps/desktop/src-tauri/src/audio/luka_repro.rs` (new) serves the engine
through one shared link: one queue, one rate, a cap on how much each response
may have in flight, 150 ms per request. Runs of the real uV18CIbSXZo body
(`luka_repro::explore`), main's engine:

| link | loads | result |
|---|---|---|
| 500 KB/s, 1 MB in flight | 1 | opens in 3.0 s (tail's first byte after 2.5 s) |
| 500 KB/s, 1 MB in flight | 2 (20 ms apart) | superseded load: stalled at 5.8 s. Current load: "stopped arriving while decoding (nothing for 3s) (on a second attempt, after: ...)" at 11.3 s |
| 250 KB/s, 1 MB in flight | 1 | stalls twice, the same message |

That is Luka's message, word for word, and his timing (10.7 and 10.8 s).

Ruled out:
- **The host serving slowly.** A slow answer to the first request falls
  under the 25 s connect budget and gives a different message. The host logged
  nothing, and every request here is answered at once. Only the queue on the
  link is slow.
- **Fragmented bodies.** The same runs with a fragmented body (TwFXwkKyGSQ as
  googlevideo serves it) open every time, even with two loads, because a
  fragmented body needs only one request (422ab02). So Luka's host has ffmpeg
  and keeps remuxed files. Songs that stall are the remuxed ones.
- **The retry racing the second load.** The retry only runs for the current
  load (`still_wanted`), and fails for the same reason as the first attempt.
  It adds a second 3 s wait, nothing worse.

### The engine fix (branch `luka-24`)

A reader blocked in a seek is waiting for the host to answer a new request.
That wait is now judged like any other request (the 25 s connect budget, from
the later of the seek and the last chunk), not as 3 s of silence. Silence
while reading, which is what a dead source looks like, is still caught at
3 s. A tail request that is never answered still fails, and says so: "the
host did not answer a request for more of the song while decoding".
`apps/desktop/src-tauri/src/audio.rs`: `SeekWatched`, `is_stalled_during`,
`LoadStop::Unanswered`.

Tests, `cargo test --lib luka_repro` (fixture `tone-faststart.m4a`):

| test | main | luka-24 |
|---|---|---|
| `ended_then_two_loads_on_a_shared_link_still_open_the_song` (80 KB/s) | fails: "(on a second attempt, after: ...)" | passes |
| `one_load_on_the_same_link_opens_the_song` (control) | passes | passes |
| `one_load_on_a_slower_link_opens_the_song` (60 KB/s) | fails, the same message | passes |
| `a_request_for_the_tail_that_is_never_answered_still_fails` | (new API) | passes |
| `a_seek_waiting_on_the_host_gets_the_request_budget` | (new API) | passes |

Full `cargo test --lib`: 64 passed, 3 ignored.

On the real body at 250 KB/s, with the fix, one load opens in 5.8 s and two
loads in 11.8 s (both failed before). Two loads still cost twice as long,
which is why P01 matters as well.

### What fixes it

1. Merge bughunt to main and run `./update.sh` on the host: P01 is web code,
   so every desktop app gets it at the next page load. This alone fixes the
   double load.
2. Release a desktop shell (0.4.2) with the `luka-24` engine fix and bughunt's
   P03 and P07. They touch different functions of `audio.rs`; merging
   `luka-24` into bughunt has one conflict, the two test module lines
   (`mod luka_repro;` and `mod transport_repro;`: keep both), and the merged
   engine passes `cargo test --lib` (88 passed, 3 ignored). This fixes slower
   links too.
3. Not done here, worth doing later: cancel a superseded load's download as
   soon as a newer load claims the engine. Today a superseded load keeps its
   requests on the link until its decoder is built. That matters for fast
   skipping, and less once P01 is in.

The desktop log attached to each automatic report (on the host, in the
report's `desktopLog`) can confirm the double load: two `load #N start` lines
for the same URL a few ms apart, then `trying once more`.

## 2. ResizeObserver loop (report 1)

`components/tabs/LiveTabScore.tsx` watches the score's width and called
`api.render()` inside the ResizeObserver callback. The re-draw changes the
host's size while the browser is still delivering size changes (AlphaTab
watches the same element with its own observer), so the browser delivers the
rest a frame later and raises this error. AlphaTab's own observer re-draws
through a timer, outside the callback, and never triggers it.

Checked in Chromium with AlphaTab 1.8.4 and a 64-bar score, width changed six
times:
- our observer as it was: 6 errors;
- our observer re-drawing in the next frame: 0 errors, the score still
  re-lays out;
- no observer of ours: 0 errors (AlphaTab re-lays out by itself).

Harmless: nothing is lost, the notifications arrive one frame later. But it
went out as an automatic report, and a session gets only three (Luka's
session used all three: this one and the two stalls).

Fixed:
- `LiveTabScore.tsx` re-draws in `requestAnimationFrame` (test: `LiveTabScore
  resize`, fails before with `expected "vi.fn()" to not be called at all`).
- `lib/logger/client.ts` records "ResizeObserver loop ..." as a warn
  breadcrumb, not an error, so it never triggers an automatic report (test:
  `ClientLogger: benign browser errors`).

## 3. numpy and basic_pitch missing (report 1, and the server errors in all three)

- `align.py` (lining a found tab up with the song) imports numpy and librosa.
  `transcribe.py` (generated tabs) imports basic_pitch and librosa.
- `requirements.txt` lists only ytmusicapi, yt-dlp and imageio-ffmpeg. The
  tab packages are there as comments, the same block as SETUP.md "Generated
  guitar tabs (optional)".
- `update.sh` upgrades yt-dlp and ytmusicapi and installs imageio-ffmpeg.
  It never runs `pip install -r requirements.txt`, and nothing installs the
  tab packages.
- Optional: yes. Everything else works without them. But alignment runs
  automatically for every tab found online, so a host without them logs
  "lining the tab up failed" as a server error on every find, and those show
  up in every report.

**The host must run** (from SETUP.md):

```bash
.venv/bin/pip install 'setuptools<80'
.venv/bin/pip install --no-deps basic-pitch
.venv/bin/pip install onnxruntime librosa pretty_midi 'resampy<0.4.3' mir_eval scikit-learn typing-extensions
```

(librosa brings numpy.) Then restart the web app. Owner's call, not done
here: have `update.sh` install this block, or have alignment log a missing
module once as a warning instead of an error per tab.

## 4. "ultimate guitar tab search failed" (reports 2 and 3)

Queries "Anime Token Music Foreground Eclipse" and "Bloody Cumshot Dogmatic
Beliefs": obscure songs with no tabs on Ultimate Guitar. Checked 2026-09-24:
UG answers a search with no results with HTTP 404, and the body is its normal
search page (`results: []`, `not_found`). `PoliteFetcher.getText` threw on
any non-2xx status, so `searchUg` logged "tab search failed" and returned
`failed`. A failed lookup is not remembered, so the next visit to the song's
tab page asked again and logged again ("seen 14 times this week").

Not a scraper breakage: a song with tabs still gets a 200 page with results.

Fixed: the search accepts a 404 and lets the page decide
(`lib/tabFetch/online.ts`, `polite.ts`). A no-results page is now "none",
remembered, with nothing logged. A 404 without UG's page data is still a
failure. Test: `lib/tabFetch/online.test.ts` "a no-results page UG serves as
a 404 ...", fails before (`expected { status: 'failed' } to match { status:
'none' }`).
