# S04. Anyone could start unlimited Python helpers on the host
**What you'd notice:** nothing until someone abuses it: a script hammering search (no sign-in needed) could start hundreds of Python processes at once and make the host crawl or run out of memory.
**Why it happened:** every search, album, artist or stream lookup starts a Python helper, with no ceiling on how many run together. The public routes had no rate limit, and the one limit that existed trusted a cookie and an IP header the caller can make up, so a fresh fake value got a fresh allowance. Its memory of callers also never shrank.
**What changed:** at most 4 helpers run at once for listening and browsing (`PYTHON_MAX_CONCURRENCY`), with separate slots for downloads (3, `PYTHON_MAX_DOWNLOADS`) and import batches (2, `PYTHON_MAX_BULK`), so a slow download never blocks a search. Extra work waits in line. If it waits too long (15 s for searches), the caller gets a clean "busy, try again" (503) instead of piling up. Public routes that start Python now have generous per-caller limits: 40 searches, 60 album/artist/track pages, 30 recommendations and 60 new song downloads a minute. Callers are identified by their PocketBase-verified account, otherwise by the IP address Tailscale Funnel reports. That is the last `X-Forwarded-For` entry: Funnel replaces whatever the caller sent, and Next fills it in for direct connections. Idle callers are dropped from memory every minute. Tab transcription stays outside the cap: it needs sign-in and is already limited to 5 an hour. Files: `apps/web/lib/semaphore.ts` (new), `lib/sources/youtube.ts`, `lib/rateLimit.ts`, `lib/auth.ts`, the public `app/api/youtube/*` routes, `app/api/search`.
**Compare:** before = `0a92744`, after = `0ec813d`.
- Test: `cd apps/web && npx vitest run lib/sources/youtube.concurrency.test.ts lib/rateLimit.test.ts lib/semaphore.test.ts app/api/youtube/search/route.test.ts`. Fails before:
  - `10 parallel searches run at most 4 Python processes at once`: `expected 10 to be 4` (all 10 processes started together)
  - `downloads have their own lane`: `expected ... to have a length of 3 but got 4`
  - limiter and route tests: `_resetBuckets is not a function` (the new keying and cleanup did not exist; the route answered all 100 flood requests)
  - Passes after: 25 of 25, including a flood of 100 searches getting 40 answers and 60 "429 slow down" replies.
- Try it yourself: on the sandbox, run `for i in $(seq 60); do curl -s -o /dev/null -w '%{http_code}\n' "http://127.0.0.1:3050/api/youtube/search?q=test$i"; done`. The first 40 answer 200, then 429.
**Risk:** low to medium. A very busy host could now show "busy, try again" on a search instead of being slow. Raise `PYTHON_MAX_CONCURRENCY` in `.env.local` if that shows up.
